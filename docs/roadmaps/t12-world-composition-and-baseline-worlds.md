# T12 — World Composition and Baseline Worlds

**Status**: Planned
**Last updated**: 2026-09-08
**Master**: [Program Roadmap](../roadmap.md)

## Goal

Make the world at tick zero a thing that can be described, saved, and
regenerated: terrain, fertility, and food types that trade value against
abundance and recovery come from one recipe and a seed, any world reachable in the app can be saved and loaded back, and a
small named set of baseline worlds, single pressures and composites of them,
is what later environmental features are read against.

## Track Success Criteria

- [ ] A world config with terrain layers and seeds regenerates the identical world in any process and at any thread count, verified inside `make check`.
- [ ] Food types can differ in energy per bite, coverage, regrowth, and recovery through the world config alone, production defaults unchanged, so a rich rare food and a poor abundant one can share a world.
- [ ] Any world reachable in the app or the CLI can be saved as a recipe and loaded back by both, and every benchmark report that reads a recipe records its path and digest.
- [ ] A named baseline world set exists in Git, each recipe with a stored persistence reading at production defaults, and every environmental mechanism feature closed after it records its readings on that set.
- [ ] Production defaults stay barrier-free, so this track's infrastructure features leave the gate and goal trajectories unchanged.

## Executable Features

- [ ] **T12.F01 — Seeded Terrain in the World Config** — Depends on: None
  - Goal: Bedrock and water. The land has a shape before anything lives on it: barrier terrain is generated from the world config and seed at startup, before food and founders are placed, so where a creature can walk and see is set from tick zero and the same recipe and seed regenerate the same world in any process.
- [ ] **T12.F02 — World Recipe Save and Load** — Depends on: T12.F01
  - Goal: A world is a file. The effective world config, terrain and seeds included, saves from the app or the CLI and loads back to regenerate the same world, so a baseline is a small recipe in Git rather than a stored map.
- [ ] **T12.F03 — Food Landscape with Tradeoffs** — Depends on: None
  - Goal: Fruit and grass. Each food type has its own energy per bite, coverage, regrowth rate, and recovery rate in the world config, with defaults equal to today's shared values, so a rich, rare, slow-returning food and a poor, abundant, quick one can share a world and what a creature eats and where it goes has consequences.
- [ ] **T12.F04 — Baseline World Set** — Depends on: T12.F02, T12.F03
  - Goal: Plains, archipelago, oasis, canyons, orchards in grassland, and where they meet. A named set of recipes built from the composition pressures the world has (fragmentation with corridors, scarcity and patchiness, occlusion and constrained paths, bounded edges, food tradeoffs), some isolating one pressure and some composing several in one world (islands with oases, canyons around a spring, islands with orchards), each checked in with a persistence reading at production defaults, so later environmental features are read against the same worlds.

## Notes for AI Agents

- Evidence base: the [world seeding research note](../strategy/world-seeding-research-2026-09-08.md) (2026-09-08). It records what already exists, the options considered, the primary literature behind the archetypes, and the decisions left to the user.
- Ownership. T12 owns what the world is at tick zero: terrain generation at startup, the recipe and its seed rule, save and load, and the baseline set. T02 owns how the world changes over time (seasons, disturbance, grazing) and the perception side of terrain (T02.F02: occlusion, creature opacity, sensor noise). T04 owns the population consequences of geography and reuses T12.F01's terrain for habitat patches. T06 owns creature-authored change to terrain. T10 owns checkpoints, which are simulation state; a recipe is config, not a checkpoint, and needs none of T10's deferred machinery. The track was created on 2026-09-08 by the same rule the master roadmap records for T11: one durable area with one invariant (a recipe and seed regenerate the same world anywhere) whose ownership was split across T02.F02, T04.F03, T06.F01, and T10.
- The world is already three-quarters procedural. Fertility is generated per layer from `layer.seed` or `world_seed + index`; food is seeded by exact coverage over passable cells with one seeded shuffle per type; founders are placed by a seeded shuffle of passable cells, clamped to their count. Barrier terrain is the only layer that is neither in the config nor regenerated from the seed: it exists today only through the paint and pattern endpoints after seeding. T12.F01 adds `world.terrain`, an ordered list of layers, each an existing `PatternParams` variant with optional `PatternBounds` (absent means the whole world) and an optional `seed`, applied in `seed_simulation` after `WorldState::new` and before fertility, food, and founders. Setting barriers there needs no food clearing or eviction, so it sets the grid directly rather than going through the paint stroke. Layers only add barriers in T12.F01; an erase mode is a candidate for T12.F03 if an archetype needs guaranteed corridors.
- World seed. T12.F01 adds `world.world_seed: Option<u64>`. Absent, terrain and fertility derive from the run seed, which is today's behavior and keeps seeds 11/22/33 as three maps; present, it fixes the map across replicate seeds while food seeding, founder placement, and the run RNG still vary. The fertility layer's per-layer `seed` stays and still overrides. This is a user decision recorded in the research note's Section 7; the default above is the recommendation.
- Reproducibility constraints that become live the moment terrain runs at seeding: `crates/v3-core/src/patterns/noise.rs` in cluster mode collects a `HashSet` into a `Vec`, shuffles it with the seeded RNG, and truncates, so the surviving cell set differs between processes (recorded as deferred by the T10.F11 spec). T12.F01 fixes it by ordering the cells before the shuffle and extends `crates/v3-core/tests/reproducibility.rs` with a terrain-bearing config. The four other generators collect sets whose order does not matter because setting a barrier is idempotent. `SmallRng` is `Xoshiro256PlusPlus` on 64-bit hosts and is documented as not reproducible across `rand` versions or platforms; T12.F01 names the generator for the world-generation path (`rand_xoshiro` 0.6 `Xoshiro256PlusPlus`, the `rand_core` 0.6 line matching `rand` 0.8), gated on a test that its stream is bit-identical to `SmallRng` at the same seed, and falls back to recording the `rand` version in the report if that test fails. The run RNG may be renamed the same way in the same feature only if the byte-identity test holds. `noise` 0.9.0 is pinned by `Cargo.lock`; an upgrade re-records every baseline that uses an `Fbm` layer.
- Schema discipline. `SimulationConfig` uses `deny_unknown_fields`, so a new world key moves in one feature through the Rust config, the server startup schema, `frontend/src/types/config.ts`, the startup panel (a Terrain section beside World Topology), and the canonical reference specs: new rows in `docs/reference/v3-world-grid-spec.md` Section 4 and a terrain step in the seeding flow of `docs/reference/v3-startup-seeding-spec.md` Section 4. The server's `MAX_PATTERN_AREA` (1,000,000 cells) applies to the runtime pattern endpoint only; whole-world terrain at 1600² (2,560,000 cells) is generated at startup. World sides are `u16`.
- Recipe format. There is no new format: a recipe is a partial `SimulationConfig` JSON, deep-merged over the current defaults by the same rule the server startup already uses. T12.F02 gives the CLI that merge rule (today `--config` requires every non-default section), adds Save (the effective config from `GET /v3/simulation/config`) and Load (a recipe file into the startup request) to the frontend, puts the config digest into the `run_started` NDJSON event, and gives `bench --profile sweep` a `--config` input whose path and digest the report's profile block records. No version field: the report's commit identifies the code and `deny_unknown_fields` fails loudly on a stale recipe, which is the right posture when backward compatibility is not a goal. `experiments/suites/` (2026-03-12, no consumer, and its startup patches set a `founder_profile` field the API spec calls unsupported even though the server accepts it) is retired by T12.F02. Hand-painted terrain is not saveable until a `Bitmap` layer variant exists; it is deferred until the user wants painted baselines.
- Production defaults do not change. `world.terrain` defaults to empty and `world.world_seed` to absent, so the gate and goal profiles run the same trajectory before and after T12.F01 and T12.F02, and neither feature re-pins the epoch baseline. If a spec finds that impossible, it predeclares the cost.
- Baselines do not replace the goal profile. The default barrier-free world stays the goal profile and is the plains baseline; the other recipes are read through the sweep profile with `--config` at three seeds and 2,000 ticks. Reading protocol from T12.F03 onward: every environmental mechanism feature (T02, T04.F03 and T04.F04, T06, and T12 itself) records the world-set readings in its spec at closure beside the goal reading; other features do not run the set; the user may request a reading at any time. Four recipes cost about 45 minutes at the goal world's 11 minutes per run. Each recipe is checked in only with a stored persistence reading at production defaults under `docs/progress/sweeps/t12-f03/`, resized until it persists or recorded as failing, and the reading records the passable fraction and the largest connected passable component so a dead world is attributed to isolation rather than to the pressure. Persistence below the default 1600² is seed-dependent (T01.F11, T11.F04), so islands and corridors start large.
- Archetypes and their evidence (research note Section 4). Single pressure: archipelago (islands and straits; fragmentation with corridors; the one new generator, an `FbmThreshold` terrain variant on the existing `noise` fBm; reads for T04.F03 and T04.F04), oasis (desert with springs; scarcity and patchiness; few large fertility blobs at `min_fertility` 0; reads for T02.F04, T02.F05, T03.F05), canyons (a whole-world `Maze` with corridors wider than the vision radius; occlusion and constrained paths; reads for T02.F02 and T09). Composite: islands with oases (fragmentation and scarcity), canyons around a spring (occlusion and a fertility gradient), a bounded desert with springs near one edge (edges and scarcity); the spec fixes the final list and keeps it small. World edge mode is a free knob for any recipe: `Bounded` adds edges and corners with no new feature. Food tradeoffs enter through T12.F03: orchards in grassland (fruit trees in grass; a rich, sparse, slow-recovering food in patches beside a poor, abundant, fast-recovering one; two food types with per-type value, regrowth, and recovery, the rich one placed by a `SingleType` fertility layer whose region partly overlaps the other, as the Avida evidence advises; reads for T03.F04, T02.F04, and the T09 assays), and its composite, islands with orchards. Limited, regionalized resources are the diversity lever (Cooper and Ofria 2002; Chow et al. 2004); phenotypic diversity rose with spatial entropy of resource placement (Dolson et al. 2017); more, smaller connected reserves maintained and generated more phenotypes once evolution was on (Dolson, Wiser, and Ofria 2016); new traits appeared at borders between resource combinations (Dolson and Ofria 2017), which is why the set composes pressures rather than only isolating them.
- Order of new starts (master roadmap, 2026-09-08): T12.F01, T12.F02, and T12.F03 follow T11.F18, the next new start by user decision later on 2026-09-08, because none changes the production trajectory. T12.F04 runs immediately before T02.F01, after T11.F13, because its stored baseline readings are what T02.F01 and the other environmental features are read against; taken before the T11 supply repairs (T11.F09, F15, F10, F13), they would make the first consumer's delta span those repairs, the same attribution problem that placed T02.F01 after T11.F13. The alternative, each consumer taking its own paired reading of the set on `main` at its start, costs about 45 minutes per environmental feature and is the fallback if the user pulls T12.F04 forward.
- Food landscape (T12.F03, user direction 2026-09-08). What exists: `world.food.types[]` gives each type a name, color, initial density, initial coverage, and a growth inhibitor against other types; `SingleType` fertility layers place a type; the `Eat` action carries a food-type index decoded from an evolvable action parameter; per-type food sensors exist. What does not: growth rate, spread, recovery spawn rate, recovery floor, and max density are shared across types, and every type pays the same `energy.costs.eat_reward_per_food`, so two types today are two colors of one food. T12.F03 adds per-type energy per unit, regrowth rate, and recovery rate (the spec decides whether spread and max density follow), each an optional field defaulting to the shared value, so the one-type production default and its trajectory do not change; `cargo test -p v3-core --test viability` runs first because eating is birth-path economics. It is not the complementary nutrition removed on 2026-09-07: no nutrient budget and no requirement to eat several types, only foods that differ in what a bite is worth and how soon the patch returns. Theory read in full for it (research note Section 4): MacArthur and Pianka 1966 rank foods by harvest per unit time and predict a narrower diet where the rich food is dense and a broader one where it is sparse, with larger patches used more selectively than small ones; Charnov 1976 predicts a forager leaves a depleting patch when its intake rate there falls to the habitat average, so a type's recovery rate sets when a patch is worth revisiting. Two consequences for the design: the pressure to prefer the rich food turns on the rich food's own density, so recipes sit on either side of that switch; and specialists resist a generalist only when the generalist's efficiency loss outweighs its travel saving, which is T03.F04's body-side digestion cost, so T12.F03 alone selects on where to go and what to eat. T02.F04's history-dependent yield later stacks on each type's constant recovery.
- Composition versus dynamics. The set is composed from what the world is at tick zero (terrain, fertility, food placement, each food's constant value, regrowth, and recovery, edge mode), and its composite recipes combine those. Dynamic pressures (T02 seasons, disturbance, grazing) are the treatments read against the set, not members of it, so no recipe enables a mechanism the set exists to baseline. Decided 2026-09-08 after user review, which merged the former composite-worlds feature into T12.F03: composites are part of the baseline set from the start.
- Options considered (2026-09-08): a stored barrier bitmap (rejected as the primary form; kept as an escape hatch), a separate world file format (rejected), reviving `experiments/suites` (retired instead), ChaCha for every seeded draw (rejected: changes every trajectory and re-pins the epoch), keeping terrain generation inside T02.F02 (rejected: couples saved worlds to seasons through an ordering dependency), scattering the features across T02, T10, and T01 (rejected: the split ownership the T11 precedent removed), replacing the goal profile's world (rejected: breaks the indicator series), and a nutrient budget across food types (rejected: that is the complementary nutrition the user removed on 2026-09-07; T12.F03 is per-type value and regrowth with no requirement to eat several types).
