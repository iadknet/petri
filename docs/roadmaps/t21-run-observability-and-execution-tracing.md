# T21 — Run Observability and Execution Tracing

**Status**: Planned
**Last updated**: 2026-09-29
**Master**: [Program Roadmap](../roadmap.md)

## Goal

Every run is identifiable and can be looked at afterwards. Each simulation
streams its identity, its configuration and many basic metrics to one local
OpenTelemetry stack, and sampled traces show what a tick did and what a
single creature sensed, considered and did. Telemetry stays cheap, with a
ceiling set from measurement and 5% of a run's elapsed time as the target
for the default, and a stopped stack never stalls or changes a run. This
track is an instrument for looking at runs: it adds no mechanism, and nothing
it stores is closure evidence.

## Track Success Criteria

- [ ] One command starts the local stack from a Docker Compose file, and its stored history survives a restart of the stack and of the host.
- [ ] Stored data is kept until the user retires it: size retention is off and time retention is set far beyond any planned use in every store, and one cleanup command retires data older than a stated date, keeps everything newer, and first shows exactly what it will remove and how much disk each store holds.
- [ ] One command-line flag turns telemetry on or off for a run; in every binary it defaults to off until T21.F05 closes and to on afterwards, and invocations that produce stored closure measurements pass the off flag explicitly.
- [ ] With telemetry on, every simulation run by `v3-server` and `v3-cli run` appears in the stack with an invocation ID, a run ID, its seed, build revision, world, full effective config and lifecycle status; a server reset starts a new run.
- [ ] Benchmark, assay and lab commands appear with identity, lifecycle and end-of-run totals, exported only after every timed region of the invocation has finished.
- [ ] The cumulative counters the runtime already maintains are exported per run as complete counts, per-tick values are exported as sampled gauges and labelled as such, and provisioned dashboards list runs and show one run's history against wall time and against ticks.
- [ ] Sampled tick traces show each phase's duration, and sampled creature traces show consecutive ticks of one creature's inputs, routing, votes, selected actions, applied outcomes and state changes.
- [ ] Every span carries its run and build identity, tick, phase, the config values and mechanism switches in force at capture, and the digest of the full effective config; a field that was not captured is marked absent, never zero.
- [ ] Every sample names the policy that selected it, so a manually targeted creature is never read as a representative one.
- [ ] With the stack stopped or slow, a run keeps its speed, holds bounded telemetry memory, ends within a bounded flush time, and records what it dropped.
- [ ] The default telemetry configuration stays under the ceiling the user sets at T21.F05 from measured cost, with 5% of elapsed time as the target, measured as total telemetry cost against a reference build with T21's work compiled out, with the stack healthy, stopped and slow; every closure before T21.F05 closes stays under the 25% interim ceiling, and every closure after it stays under the ceiling F05 recorded.
- [ ] A seeded run produces byte-identical deterministic output with telemetry on, off and with the stack stopped, and with telemetry off it matches the build of the feature's parent commit; telemetry consumes no production RNG and no telemetry setting enters the config digest.
- [ ] The feature spec template has a telemetry section, and the final review checks it.

## Executable Features

- [ ] **T21.F01 — Local Telemetry Stack and Run Identity** — Depends on: None
  - Goal: Measurement tooling. One command starts a local stack that keeps its data until the user retires it, and a run started with the telemetry flag appears in it with its identity, full config and start and end status, while a stopped stack changes nothing about the run.
- [ ] **T21.F02 — Run Metrics and Dashboards** — Depends on: T21.F01
  - Goal: Measurement tooling. The cumulative counters a run already keeps are exported per run as complete counts and its per-tick values as sampled gauges, and provisioned dashboards list runs and show one run's history against wall time and ticks.
- [ ] **T21.F03 — Tick and Phase Tracing** — Depends on: T21.F02
  - Goal: Measurement tooling. A sampled tick becomes one short trace whose spans show how long each phase took and the config and world state in force, reachable from the run's dashboard.
- [ ] **T21.F04 — Creature Cognition Windows** — Depends on: T21.F02
  - Goal: Measurement tooling. A selected creature is recorded for a short run of consecutive ticks, showing what it sensed, how its brain routed and voted, what it chose, what the world actually applied and what changed in its state, reachable from the run's dashboard.
- [ ] **T21.F05 — Qualified Sampling Defaults** — Depends on: T21.F03, T21.F04, T21.F06
  - Goal: Measurement tooling. The cost of each level of detail is measured, the user sets the default's ceiling from it with 5% as the target, the default export cadences and sampling caps are chosen to stay under it with margin, with named presets and their measured time and storage costs, and telemetry becomes on by default in every binary.
- [ ] **T21.F06 — Benchmark, Assay and Lab Run Records** — Depends on: T21.F02
  - Goal: Measurement tooling. Benchmark, assay and lab commands appear in the stack with identity, lifecycle and end-of-run totals, held in memory and exported only after every timed region of the invocation has finished, so stored measurements do not move.
- [ ] **T21.F07 — Telemetry Conventions in the Feature Contract** — Depends on: T21.F02
  - Goal: Measurement tooling. The feature spec template's telemetry section names the delivered conventions, and a feature that adds a mechanism or counter ships its exported signals with it.

## Notes for AI Agents

- Evidence and design: the [run observability research note](../strategy/run-observability-research-2026-09-29.md) (2026-09-29). It starts from the user's requirements and the code and does not inherit the T21 draft that the 2026-09-27 revert (`a26c1cf0`) rolled back. Do not read that draft as a source of requirements.
- User decisions, 2026-09-26, restated 2026-09-29: the stack is local; outages may leave gaps and the simulation keeps running; telemetry costs at most about 5% (amended below); the track skips the benchmark profiles and the mutation gate; it can be worked concurrently with T20; the feature spec template gains a telemetry section; spans carry as much context as possible, including feature state and config values.
- Overhead ceiling (user decision, 2026-09-29). The 5% ceiling is relaxed to start. The ceiling in force follows qualification state, not feature number: every T21 closure before F05 closes is held to an interim ceiling of 25% more elapsed time, and every closure after it, including F06, F07 and any later feature that adds work to a run, is held to the ceiling F05 recorded. The interim ceiling exists because 5% costs many paired runs to prove, telemetry is opt-in until a default is qualified, and closure benchmarks run with it off. 5% stays the target for the default configuration: F05 measures cost against detail and the user sets the final ceiling from that data. Telemetry is not made default-on while its cost sits at the interim ceiling. Three guarantees do not relax: seeded output is byte-identical with telemetry on or off, a stopped stack never stalls a run, and telemetry memory stays bounded.
- **Not closure evidence.** The master roadmap's program-tracking rule ("no dashboard, database, service, or composite success score") and T14's observation contract govern how the program is judged, and they stand. The T21 stack is for looking at runs. No dashboard reading closes a feature, sets a default, becomes an indicator or replaces `docs/progress.md` and the stored summaries. A number that matters to a decision is reproduced by a stored report or a lab reading and cited from there.
- Ownership. T21 owns `crates/v3-telemetry`, the Compose stack and its provisioned configuration and dashboards, run identity, export, sampling policy and the mapping from Petri data to metrics, spans and log records. T14 owns the stored closure report and the definitions of the runtime counters; T21 exports those counters unchanged and redefines none. T22 owns `crates/v3-lab`; T21.F06 adds only run records to it. A counter or reading a mechanism feature introduces stays with that feature.
- Boundary. `v3-core` takes no OpenTelemetry dependency and holds no exporter state. It exposes plain data: counter snapshots, phase timings and recorder output for a requested creature. The binaries pass that data to `crates/v3-telemetry`. Neither `v3-core` nor `v3-lab`'s library depends on the telemetry crate's SDK types.
- Measurement features: the natural-analog rule and the environmental-pressure baseline rule do not apply, and no T21 feature adds a pressure, simulation default, founder change or mutation policy. The telemetry flag's default is a process-level setting, not a simulation default, and F05 is the feature that changes it.
- Verification (user decision). T21 features skip the gate and goal benchmark profiles and the mutation gate. The exemption, its conditions, and the triggers, method, time cap and ceiling rule of the track checks that replace the skipped gates are in the [workflow's Benchmark gate](../workflow.md#benchmark-gate). This track states only who delivers each check and what it must show.
- Telemetry-neutrality test (F01 delivers it, inside `make check`). A seeded run's deterministic output is byte-identical with telemetry off, with telemetry on, and with telemetry on and no stack listening. It is seconds-scale and needs no Docker.
- Parent comparison (F01 delivers the command). It must show that the changed build with telemetry off behaves as its parent build does: byte-identical output on the same seeded run. It exists because the neutrality test compares the changed binary with itself and cannot see a behavior change that lands on both paths. The parent is the feature's merge base, so both sides hold identical simulation code from every other track.
- Reference build (F01 delivers it). One build switch compiles out everything T21 adds: the telemetry crate's use in the binaries and every observation seam T21 adds to `v3-core`. The reference is the same commit built with that switch off, so it holds the current simulation and none of T21's work. It is the only baseline for cost. No fixed earlier commit is a baseline, because other tracks keep changing the simulation.
- Overhead check (F01 delivers the command). It must show total telemetry cost, including the stack's own contention on the host, under the ceiling in force, measured against the reference build. Until F05 closes it covers one world and two stack states (healthy, stopped). F05's qualifying measurement covers at least one default-size world and one small one and three stack states (healthy, stopped, slow). F01 also records what an idle running stack costs a run that has telemetry off. Telemetry's self-timed cost per tick is recorded beside the ratio: it attributes only the time spent inside telemetry calls on the simulation thread, so it is a lower bound that is steady when wall time is noisy, not a measure of total cost.
- Budget arithmetic, from the stored T11.F27 goal summary: about 9.7 ticks per second and 15.8 µs per creature-tick, so 5% is about 5 ms per tick and 0.8 µs per creature-tick. The SDK's own benchmark creates a span in 1.1 to 2.5 µs. A span per creature per tick cannot fit; creature detail is sampled, and the decision to record is made before anything is recorded.
- Sampling contract. Cumulative counters are never sampled: the run loop copies them to the exporter on a cadence, and a cumulative count read late is still complete. `SimStats` also holds per-tick values (`last_tick_*`) that `reset_tick_counters` clears every tick; copied on a cadence they are sampled gauges and are labelled as such. A per-tick value advertised as a complete count is accumulated before the reset, by the exporter's snapshot and never by changing what the counter means. Sampling applies to expensive observations. Controls are hard caps per tick and per wall second (windows, spans, bytes, queue length), not a percentage of the population, so cost does not grow with population or speed. Selection is a pure function of run, creature and window, or a separately seeded stream; it never draws from production RNG. Collector tail sampling cannot protect the ceiling, because the run has already paid. An adaptive governor is held in reserve until F05 shows fixed caps fail.
- Context contract. Prefer fewer samples that explain themselves. Each span carries run and build identity, tick, phase, and the config values and mechanism switches that govern the code it describes, read at capture. The full effective config is one log record per run and one per server config change, keyed by digest; spans carry the digest. A payload too large for a span (a genome, a full perception snapshot) is logged once per window and referenced by hash. When the payload costs too much, lower the sampling rate before removing context. Each feature spec lists its attributes and their sources in a table.
- Applied outcomes. The recorder stores selected actions. F04 joins each to what the action phase applied: success or failure, realized cost, and the resulting change. Telemetry derives from applied behavior, as `AGENTS.md` requires.
- Recorder. `run_cognition` traces one creature, removed from the parallel work list and run sequentially. F04 starts from that: one creature window at a time, the target moving to the next selected creature when a window ends. Recording a set of creatures at once is added only if F04's measurements show one window at a time gives too few samples. F04 separates two costs: the unconditional cost of having the recording path present, which the reference build reads, and the cost per recorded creature-tick, which fewer windows reduce. `ActiveTrace` and `TickTrace` hold nested vectors that grow with hops and passes and have no byte limit, so F04 enforces its budget during capture: when a window reaches its event or byte cap, capture stops, the creature's execution continues unchanged, and the sample is marked truncated. The traced and untraced paths produce identical decisions.
- Run identity. An invocation is one process; a run is one simulation from seed or reset to its end. Every signal carries both. The invocation ID is a resource attribute, set once per process. The run ID is a metric attribute, because one server process holds many runs; it is the only high-cardinality metric attribute and sits on a bounded metric set. Creature IDs, ticks, lineage IDs and genome hashes appear on spans and log records only, never as metric attributes.
- Time. Metric timestamps and span durations are wall time. Every span and log record carries its tick as an attribute. Metrics never carry the tick as an attribute: each counter snapshot exports a tick gauge taken in the same copy, so a dashboard places any metric on the tick axis by joining on that gauge. Traces are short: one per sampled tick, one per creature window. No trace spans a run.
- Configuration. Telemetry settings are process-level flags and environment variables. None enters `SimulationConfig` or `RuntimeConfig`; the config digest and the pinned recipe digests do not move.
- Telemetry flag (user decision, 2026-09-29). Every binary that runs a simulation takes one command-line flag that turns telemetry on or off for that invocation, and an explicit flag wins over any environment variable. F01 delivers it with the default off everywhere, so telemetry is opt-in per run. F05 flips the default to on in every binary, in the same change that qualifies the default configuration; F06 closes first so measurement commands already export safely when their default flips. Two kinds of invocation pass the off flag explicitly from F05 on: tests that start a binary, so `make check` needs no Docker and behaves as before, and invocations that produce stored closure measurements (`make bench` and the closure profiles), so closure evidence is taken in isolation. Whether closure measurement runs later export too is part of D2.
- Failure behavior. Export is best effort: bounded queues that drop when full, bounded retries, a bounded shutdown flush. Dropped counts and export failures are recorded so a gap reads as a gap. Nothing is buffered to disk for later upload.
- Measurement commands (F06). Benchmark, assay and lab commands are covered by the all-runs requirement, so their export is required, not optional. With telemetry on, a measurement command captures its run records at region boundaries, holds them in bounded memory, and starts no exporter activity until the final timed region of the invocation has finished; `bench/run.rs` times several cases and observations in sequence, so exporting between them would compete with the next one. No span or metric is exported from inside a loop. F06 delivers a small fixture inside `make check` that runs a measurement command with telemetry on and off and shows three things: the deterministic fields of its output are identical, records are captured only at region boundaries, and the exporter is not started before the final timed region ends. Wall-clock readings are compared statistically under the overhead check; they are never promised identical. What is open is D2: which end-of-run totals are recorded, and whether closure measurement runs export.
- Storage (user decision, 2026-09-29). Data is kept indefinitely. Prometheus cannot switch time retention off, so indefinite means configured: size retention off and time retention set far beyond any planned use, with the value stated in F01's spec, in Prometheus (default 15 days) and Tempo (default 14 days); Loki deletes nothing unless compactor retention is enabled, and it is enabled with a retention period of zero only so that delete requests work. Old data is retired ad hoc by a cleanup command F01 delivers as a POSIX `sh` script behind a `make` target. It takes a cutoff date, prints each store's disk use and the exact targets it would remove, and deletes only when told to proceed. Its contract is the same for every store: everything newer than the cutoff is kept, the preview names what goes, and the procedure is the store's own supported one, verified in F01 on a scratch volume before it touches real data. Prometheus deletes through its admin API (`delete_series`, then `clean_tombstones`) and Loki through its delete-request API. Tempo has no delete API and stores traces in blocks, so the script removes only whole blocks that end before the cutoff, with Tempo's writers and compactor stopped; a block that straddles the cutoff is kept whole, and the script reports that granularity. Retiring one run by ID is available where the store supports it and is not promised for traces. Disk use grows without bound by design, so starting the stack prints current use, and F01 records measured bytes per run so growth can be projected. Nothing the stack stores is committed; the Compose file, stack configuration, dashboard definitions and the cleanup script are source. Under the telemetry commit rule, every feature that adds a trace predeclares its projected size per run and its per-run cap in its spec; the cap bounds what a run emits, not what the stack keeps.
- Transport. OTLP over HTTP with the blocking client runs unchanged in the synchronous CLI and the tokio server. The Rust trace SDK is Beta; versions are pinned and new crates pass the dependency policy and audit checks.
- Stack layout (user decision, 2026-09-29). Start with the bundled `grafana/otel-lgtm` image in a Compose file with a pinned version, one data volume and a container CPU and memory limit. F01's spec verifies three things on that image before it commits to it: the Prometheus and Tempo retention settings take effect and survive a restart; the cleanup procedure above works for each store; and stored data survives a change of image version. If any of the three fails, F01 uses separate Collector, Prometheus, Tempo, Loki and Grafana services instead and records the failed check; that fallback needs no further user decision. A failure that separate services share, such as a store that cannot meet the cleanup contract, is not fixed by the fallback: F01 records it as a blocker for the user. Petri speaks only OTLP to `localhost`, so either layout touches no Rust, and the bundled image keeps each store's data in its own directory in the standard format, so a later move carries the data.
- Concurrency with other tracks. T21 depends on no other track and none depends on it. Its code lands in a new crate, the binaries' wiring, the stack directory and a few observation seams in `v3-core`. A T21 feature that must edit a file another active feature is editing waits or coordinates through the workflow's concurrent-sessions rule; it never takes over a worktree.

F01 has no open user decision; its three stack verifications can still end in a recorded blocker. Still open, with recommendations in the research note: which end-of-run totals measurement commands record and whether closure measurement runs export (D2, needed before F06), and the default's final ceiling (D5, decided at F05).
