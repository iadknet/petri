# T21.F04 readings

## Options weighed at planning (2026-09-29)

| Decision | Chosen | Against | Why |
| --- | --- | --- | --- |
| Per-hop and per-action detail | span events on the `creature_tick` span (OTLP `Span.events`, each with attributes) | one span per hop and per action | about 14 records per creature-tick at goal-world rates; events carry no IDs, parents or repeated identity, cost no SDK span creation, are stored and returned whole by the pinned Tempo and reachable by `event:name` and `event.<attr>` (probe below); a span per hop would multiply the identity attributes by 14 |
| Vectors (neighbor inputs, votes, shared memory) | OTLP array-valued attributes | one attribute per element (`petri.x.0`, `.1`, …), F03's per-food-type pattern | 27-element vote vectors as 27 attributes per hop would dominate the payload and the trace view; the pinned Tempo stores arrays and matches elements (`span.petri.neighbor_food = 0.25`) |
| Budget enforcement | in `v3-core`'s recording mode at `record_hop` and `record_pass`, behind `telemetry-seams`: event count and in-memory size counted before storing | at encoding in `v3-telemetry` | the track requires the budget during capture; `ActiveTrace` and `TickTrace` hold nested vectors with no limit, so only the recorder can bound memory (a VM hop can hold up to `max_vm_steps` step records); encoding-time truncation applies only to the sampler's unbudgeted manual samples |
| Backend detail (VM steps, graph evaluations) | recorded in memory under the byte cap, not exported | export as events; add a recorder switch to skip it | exporting it would put hundreds of records per hop on the wire; a skip switch would change the recording mode's record shape for the sampler; memory is already bounded by the byte cap and the server's sampler keeps serving the detail over HTTP |
| Applied outcomes | copied from the traced creature's `ActionLog` entries of the tick inside `run_tick`, before removal, plus `OutcomeAccumulator` damage and offspring | read the log in the binary after `run_tick` | a creature that dies in the action phase is removed with its log inside `run_phase_2`, so a read after `run_tick` loses the actions it applied before dying |
| Selection | pure function of seed, window index and population over `sim.creatures` iteration order; windows start on a wall interval | a separately seeded `SmallRng` stream; a fixed tick cadence | no stream to carry across runs and resets; the same seeded run picks the same first creature; a wall interval keeps the recorded creature-ticks per wall second bounded whatever the tick rate, as F02's snapshot cadence does |
| Manual sampler | exported at `get_sample` hand-over with policy `manual`, taking precedence over an automatic window | not exported; exported at completion inside `after_tick` | the track's success criterion requires every sample to name its policy so a manual target is never read as representative; the research note lists manual samples as exported; hand-over is the one point where the sample is complete and taken exactly once |
| Genome | one `creature.genome` log record per window, body the key-sorted JSON, referenced by SHA-256 | on the root span; once per creature per run | the context contract's rule for payloads too large for a span; per-creature dedup would need per-run state for every creature seen |
| Trace identity | run key high 64 bits, then `2^63 + k` | run key low 64 bits, then `k`; OS entropy | guaranteed disjoint from tick traces (ticks never reach `2^63`) rather than probabilistically; addressable from the run ID and the window index |
