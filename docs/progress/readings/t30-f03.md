# T30.F03 — Sensors Read Views: readings

Planning record for [the spec](../../specs/roadmap/t30-f03-sensors-read-views.md).
The row pays G9, G14 (sensor caches) and G20 of
[`docs/architecture.md`](../../architecture.md) with no behavior change; the

## Options weighed at planning (2026-10-26)

No external dependency is in question: the one container the design needs,
`slotmap::SecondaryMap`, is already used by the scheduler
(`simulation/simulation.rs:26`, `simulation/seeding.rs:82`). The research
was of the local code and the architecture's rules.

| Question | Options | Chosen, and why |
| --- | --- | --- |
| Shape of the body view | (a) a `Copy` value `BodyView` and a per-tick `SecondaryMap<CreatureId, BodyView>` the scheduler fills; (b) a `BodyLookup` trait the scheduler implements over its `SlotMap`; (c) a closure `Fn(CreatureId) -> Option<BodyView>` resolved per nearby slot; (d) `&[BodyView]` indexed by slot position | (a): the view is explicit data, which is what section 3's prohibition asks for, and it is reusable by any caller (the server's inspector, tests) without a creature; (b) is a trait where a map suffices (rule 3); (c) hides which bodies exist behind a callback and rebuilds a view on every lookup; (d) couples sensors to slot-map internals. Cost of (a): N view builds per tick, which replace the N `unit_rgb` and `energy_scale` calls `assemble_static_inputs` makes today and the up-to-four per observer that `fill_nearby_banks` makes. |
| Owner of the perception-requirements value | (a) a `contracts::PerceptionRequirements` (two flags) with the key family classification on `WorldInputKey`; (b) `sensors` derives it from the creature's cached declared key set; (c) genome analysis returns an all-node declared `WorldKeySet` and sensors derives the flags | (a): the genome imports only contracts, so the value its analysis returns must be a contracts type, and which family a key belongs to is catalog data beside `compound_width` and `nearby_idx`. (b) changes which creatures get perception assembled: today's predicates walk every node, the declared cache only reachable ones, and the spec does not prove an unreachable node never executes. (c) adds a second key set per creature to carry two flags. |
| When the requirements are computed | (a) once per birth on the creature record, as the other genome-derived caches; (b) per tick from the genome as today | (a): the genome does not change after birth (rule 5 leaves the time to the row); today each creature pays two full walks of its nodes' `input_refs` per tick plus two more in a traced tick. |
| Where `WorldKeySet` lives | (a) stays in `sensors::reads`; (b) moves to `contracts` (the track note's alternative) | (a): G9 is the cycle, and once sensors stop importing the creature record, `creature → sensors::reads` is a downward import the order allows; genome analysis returns `BTreeSet<WorldInputKey>` as `creature_declared_world_inputs` already does, and the creature record collects as today. (b) is a move with no import it fixes. |
| Where the census analysis goes | (a) a new `creature/genome/sensor_analysis.rs` beside `cgp_analysis.rs` and `mesh_annotations.rs`; (b) into `genome/analysis.rs` (532 lines of mesh and VM slicing); (c) stays a reader the creature record keeps calling | (a): one module for every structural read of the sensor surface (census, declared keys, requirements, barrier reader, live VM reads), which T30.F07 moves with the genome directory. (c) leaves G14. |
| The perception-mix seeding fixture | (a) edit the founder genomes before construction through a per-founder hook on the seeding path; (b) rebuild the creature with `CreatureState::new` after the edit; (c) keep `refresh_sensor_caches` and extend it to the new cache | (a): every cache derives from the built genome and the method goes. (b) rebuilds from a genome whose birth seeds were already taken (founders carry none today, so it would work by accident). (c) extends an unmarked workaround that already leaves four caches stale (audit R5). |
