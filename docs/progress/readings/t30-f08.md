# T30.F08 — A Creature's Genome and Its Derived State Agree: readings

## Options weighed at planning (2026-10-26)

Inputs: the T30 row and its Notes entry for F08 (G27; the user's quote
"encapsulate finalized genomes and their derived state behind construction
operations, so fixtures stop swapping genomes and resyncing caches by
hand"), the track [design review](t30-design-review.md) section "T30.F08
row" (finding 1: no constructor accepts derived state apart from its
genome), `docs/architecture.md` rules 1 and 5, section 3 and debts G4, G27,
the T30.F02 spec (non-goal: "making the record's fields private (G27,
T30.F08)"; invariant 2: `GraphRuntimeState`'s fields, visibilities and
methods are runtime's), the T30.F07 spec (paths), and the code on
`a03a3692`. The decision is an encapsulation inside one crate with no
external component to adopt: the Rust idiom for an invariant-bearing
aggregate is private fields, one constructor that establishes the invariant,
and read accessors (the "make invalid states unrepresentable" pattern the
Rust API guidelines and the Rust Book's "encapsulation" chapter describe);
the crate already applies it to `cached_perception_requirements`
(`98ca76d0`, T30.F03). No library or external tool applies.

Scale on `a03a3692`: writes to a record's genome, caches or runtime outside
`creature/state.rs` at 54 lines in 14 test files (v3-core 10 files,
v3-cli 2, v3-server 1, v3-telemetry 1); production reads of `.genome` at
about 60 sites in 22 files, of `cached_*` at 55 sites in 17 files, and of
`graph_runtime` at 14 production sites; `CreatureState::new` has 44 callers
and `new_with_cached_fields` one (`spawn_child`'s zero-event branch).

| Question | Options | Chosen, and why |
| --- | --- | --- |
| How the genome and derived state are protected | private fields with read accessors on `CreatureState`; a `FinalizedGenome` newtype holding genome and analyses; `pub(crate)` fields | Private fields with accessors: `pub(crate)` still lets the 10 v3-core test files swap genomes (the bulk of the writes); a newtype adds a second aggregate whose only reader is the record, and the architecture places "one birth constructor" on the creature record (section 3), so the record is the owner that establishes the correspondence. The eight analyses are grouped in one private value computed by one function, so the correspondence is one assignment rather than eight. |
| What happens to the zero-event fast path (`new_with_cached_fields`) | keep it, reusing the parent's analyses through an operation on the parent record that takes the draft's birth seeds, not a genome (the caller cannot pair a foreign genome with the analyses); delete it and compute every birth's derived state from the genome it stores | Delete: one constructor is the simplest form of "set together by construction", and the reuse operation would clone the parent's genome a second time (the draft is already a clone) to avoid analyses of the same order of cost (walks over about a hundred nodes), so its saving is doubtful. Values are identical either way; the gate measures the cost. Fallback if the gate shows a compute regression beyond its threshold: the parent-record operation above, taking `Vec<Option<BirthSeeds>>` after `take_birth_seeds`. The default rate (0.006 per unit, about 0.6 requested events on a founder-sized genome) makes the zero-event path about half of births, so the gate is the right instrument. |
| How the scheduler reaches the brain's parts | a `brain_mut()` view on the record holding exactly the references `execute_creature_mesh*` take; `execute_creature_mesh` taking `&mut CreatureState` (forbidden: runtime is below creature); record operations wrapping the three mesh variants, `begin_tick` and the reward update | Record operations: field-disjoint borrows are impossible once `genome` is private; a view handing out `&mut GraphRuntimeState` lets any caller replace the runtime with one built for another genome (Codex round 1, F1), while an operation hands runtime its state for one call and returns the output unchanged; the runtime's signatures stay as T30.F02 fixed them. Five thin wrappers (plain, traced, budgeted under `telemetry-seams`, tick preparation, reward) are the cost. Tests reach per-tick and post-birth learning state through one `#[cfg(test)]` accessor rather than eight forwarding setters over runtime's public fields (T30.F02 invariant 2). |
| How tests obtain a creature with a given genome or learned values | `seed_simulation_with_founder_genomes` (edits the founder genome before construction; exists since `98ca76d0`, used by 3 files); `CreatureState::new` replacing the record under the same id and position (the `with_vm_founders` pattern, `window_seam.rs:40-60`, and `opportunity/assay.rs:183`); a new `with_genome(&self, genome)` record operation; learned values as birth seeds (`CgpGraphBackendDef::seed_birth`) that the constructor takes | The two existing operations: both already express "construct from this genome", and a `with_genome` operation would be a third public constructor that T29.F01 (G4) replaces anyway. Learned values go in as seeds: that is the production path (`newborn.rs`), so a test's learned state is built the way a child's is. Per-tick runtime state a test sets (`node_state`, scratch, `dispatch_record`) is runtime's own public state (T30.F02 invariant 2) reached through `graph_runtime_mut()` in-crate. |
| Tests that fabricate a cache no genome has (`cached_genome_size = 4/7/10/25`, `cached_complexity = 3/4`) | build a genome with that size or complexity and assert it; keep a test-only cache setter | A genome with the property: `genome_size()` is a count (`genome/mod.rs:325`: one per node, input ref, target, instruction, constant), so a one-node VM genome of `n` instructions has size `n + 1`; complexity is `analysis::functional_complexity`. A setter is the hole G27 names. |
| Verification profile | `none` (values unchanged by construction); `gate`; `gate + goal` | `gate`: the track's verification note declares each row gate with pins unchanged; the fast-path deletion is a cost question the gate's compute threshold answers in seconds; no population reading is in question. |
| Slow tier | `run` because `crates/v3-lab` files change (`eval.rs`, `campaign.rs` read through accessors); `not run` because they change read lines only | `run`: the workflow's trigger is categorical ("a change to `crates/v3-lab`"), as T30.F07 applied it for import-line changes. |
